Smart Global Search

Finding a supplier, oven, recipe, or purchase order meant already knowing which of eight-plus separate list pages it lived on. I designed a unified global search that lets users look anything up from one place.

Overview

Proofline, a fictional platform standing in for the real, confidential product, spans formulations, ovens and production lines, ingredients, production runs, bakeries, purchase orders, suppliers, and users, each living on its own dedicated list page, with no single entry point to just look something up.

Global search is one feature within a much larger system; this case focuses only on that feature.

The Problem

The platform had grown to cover a wide operational surface (recipes, ovens and proofing chambers, ingredient items, production runs, bakery sites, purchase orders, suppliers, users), each living on its own dedicated list page. Finding something meant already knowing where to look, navigating there, then filtering manually. This slowed down day-to-day work for food technologists, bakers, and buyers who needed to cross-reference information across entity types constantly.

Research & Discovery

I inventoried every entity type that mattered to users, and for each one defined exactly which fields were searchable and what “found” should mean:

  • Equipment: ovens and proofing chambers, searchable by name, type, and display name
  • Formulations: searchable by name
  • Ingredients: searchable by name, SKU, or supplier item number, restricted ingredients must never surface for users without access
  • Production Runs, Bakeries, Purchase Orders, Suppliers, Users: each with its own primary identifier and detail-drawer or redirect behavior

Two problems needed a real design answer, not a default:

  • Ranking. A query could plausibly match many things across entity types. I applied a consistent three-tier hierarchy, Exact Match → Starts With → Contains, across every entity type, so sorting logic never had to be relearned per section, and tagged true exact matches explicitly so users could trust the top result at a glance.

Testing & Solution

Because this search surfaced data owned by many different teams, I treated permission handling as a design requirement, not an engineering afterthought: restricted formulations and ingredients never appear in results regardless of match quality, and user search is limited to verified internal users only.

Impact & Learnings

  • Delivered a single, predictable search pattern that scaled across eight-plus very different entity types without bespoke UX per section.
  • Access control designed in from the start meant permission edge cases never became post-launch bugs.
  • A specification precise enough that engineering and QA implemented and verified it independently.

Key takeaway: The ranking logic and permission model had to be decided once and applied everywhere, the moment one entity type bent the rule, the system would have needed a legend to use. That discipline is also what let engineering and QA build against the spec without coming back to me.
